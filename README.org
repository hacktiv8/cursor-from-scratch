* Personalisasi Agen Cursor
#+OPTIONS: toc:nil

Materi untuk Cursor.id Meetup Agustus: personalisasi & workflow Cursor agent.

** Pembuka

Sebelum mulai, mari kita kenalan dulu: *Cursor* adalah code editor berbasis VS Code yang punya AI / LLM bawaan untuk bantu kita menulis kode. Jadi bukan cuma text editor biasa — Cursor bisa membaca seluruh isi proyek kita, mengedit file, menjalankan perintah terminal, dan membaca hasilnya. Inilah yang disebut /coding agent/: AI yang bisa melihat file proyek, mengedit kode, menjalankan perintah terminal, dan membaca hasilnya — bukan cuma chat biasa kayak ChatGPT.

PENTING: Cursor punya beberapa mode interaksi. Materi ini mengasumsikan kamu menggunakan *Agent mode* (bisa diakses via =Cmd+I= di macOS atau =Ctrl+I= di Windows/Linux), bukan Chat mode. Agent mode bisa membaca proyek, mengedit file, dan menjalankan terminal — Chat mode hanya untuk tanya-jawab.

Nah, LLM (Large Language Model — model AI yang bisa memahami dan menghasilkan teks, contohnya GPT-4, Claude, Gemini) ini sifatnya sulit diprediksi atau "liar" — tanpa system prompt yang jelas dan pada temperature default, LLM cenderung memberikan hasil yang bervariasi untuk prompt yang sama. Satu perintah bisa bisa diinterpretasikan berbeda-beda oleh LLM. Mari kita lihat contoh prompt yang bisa beragam artinya.

#+BEGIN_SRC text
Buat aplikasi web yang menampilkan tanggal dan jam saat ini secara realtime
#+END_SRC

Prompt diatas sederhana banget, tapi bisa diinterpretasikan dengan cara yang sangat berbeda. Coba lihat:
- Interpretasi A: CLI tool yang nge-print date ke terminal setiap detik
- Interpretasi B: Full-stack web app dengan WebSocket untuk real-time update
- Interpretasi C: Static page dengan JavaScript =setInterval= sederhana

Hasilnya bisa beda jauh kan? Padahal prompt-nya sama persis. Inilah kenapa kita perlu struktur.

Contoh 5W1H untuk prompt yang sama:
- =What=: Aplikasi web yang menampilkan waktu realtime dengan perbandingan zona waktu
- =Why=: Membandingkan zona waktu Indonesia dengan kota global
- =Who=: Pengguna yang perlu koordinasi lintas zona waktu
- =Where=: Browser desktop dan mobile
- =When=: Digunakan kapan saja, update setiap detik
- =How=: Astro + vanilla CSS + JavaScript =setInterval=

Lalu bagaimana solusinya? Gunakan framework seperti 5W+1H (What, Why, Who, Where, When, How) atau user-story template untuk memastikan prompt mencakup: aktor, aksi, input, output, dan batasan — bukan cuma "sedetil mungkin" tanpa arah.

Intinya kita harus *memikirkan apa yang mau kita buat dan bagaimana caranya dan komunikasikan ke LLM*. LLM tidak bisa membaca pikiran — jika instruksi kita tidak eksplisit, hasilnya akan bergantung sepenuhnya pada bias training data-nya. Jadi kalau kita sendiri nggak jelas mau bikin apa, jangan kaget kalau hasilnya juga ngaco.

Alat bantunya banyak wujudnya. Dua kerangka yang akan kita gunakan di materi ini adalah *piramida berpikir* (kerangka untuk memecah masalah dari abstrak ke konkret, makin ke bawah makin detail), dan *5W1H* (metode menjawab =What=/=Why=/=Who=/=Where=/=When=/=How= untuk menjelaskan sesuatu secara lengkap).

#+CAPTION: Contoh thinking framework: piramida berpikir memecah masalah dari abstrak (atas) ke konkret (bawah). Logical → Analytical → Computational → Procedural.
#+NAME:   fig:ThinkingFramework
[[./thinking-framework.png][Diagram piramida berpikir: empat lapisan dari atas ke bawah — Logical, Analytical, Computational, Procedural]]]

Mengapa ini penting untuk LLM? Karena LLM melihat seluruh instruksi dalam jendela konteks sekaligus — semakin abstrak instruksi, semakin banyak asumsi yang harus dibuat model untuk mengisi kekosongan detail. Dengan memecah dari abstrak ke konkret, kita mengurangi ruang interpretasi di setiap langkah. Bayangkan seperti kita ngasih petunjuk ke orang: kalau kita cuma bilang "bikin aplikasi", hasilnya bisa macem-macem. Tapi kalau kita jelasin dari konsep besar sampai detail teknis, hasilnya jauh lebih terarah.

Berikut contoh pemetaannya, dari yang paling abstrak ke yang paling konkret:

**** Logical thinking: /apa/ yang mau kita buat
Ini level paling atas — kita mendefinisikan ide besarnya. Untuk contoh kali ini, kita representasikan dalam format /product brief/ atau /product description/. Contoh: "Aplikasi web yang menampilkan tanggal dan jam realtime untuk berbagai zona waktu di Indonesia."

**** Analytical thinking: /apa yang dibutuhkan/ untuk membuatnya
Di level ini kita tentukan alat dan bahannya. Untuk contoh kali ini, kita representasikan sebagai /tech stack/ yang digunakan. Contoh: "Frontend pakai Astro + TypeScript, styling pakai vanilla CSS, nggak perlu backend."

**** Computational thinking: penjelasan /mendetil/ dari apa yang mau kita buat
(Catatan: Istilah "computational thinking" disini kita adaptasi dari definisi aslinya di dunia CS education — yang mencakup decomposition, pattern recognition, abstraction, dan algorithm design — untuk konteks spesifik coding agent: memecah ide besar menjadi bagian-bagian kecil yang bisa langsung dikerjakan oleh LLM.)

Di sini kita pecah ide besar jadi bagian-bagian kecil yang bisa dikerjakan. Bisa direpresentasikan sebagai fitur-fitur utama, lalu dipisah menjadi *slices* (potongan fitur kecil yang bisa dikerjakan dan di-review dalam satu waktu), *milestone* (tonggak pencapaian dalam pengembangan), *user stories* (deskripsi fitur dari sudut pandang pengguna), tiket, dll.

**** Procedural thinking: /bagaimana/ membuatnya agar terwujud
Level paling konkret — kita kasih instruksi sedetil mungkin. Contoh: batasan proyek, fitur apa yang dipilih untuk dikembangkan, mana yang belum perlu dikembangkan, dan fitur mana yang "dibuang". Juga termasuk /coding standard/, aturan testing, dan workflow yang kita mau.

Keempat lapisan diatas adalah kerangka yang kita adaptasi dari berbagai framework pemecahan masalah (seperti Bloom's taxonomy dan computational thinking) — khusus disederhanakan untuk memudahkan kita ngasih instruksi ke coding agent.

Jika keempat lapisan ini didokumentasikan secara lengkap, hasilnya setara dengan *PRD* (Product Requirements Document — dokumen yang menjelaskan fitur apa yang harus dibuat) atau *SPEC* (spesifikasi teknis — dokumen yang menjelaskan bagaimana cara membuatnya), tergantung seberapa teknis detail yang kita tulis.

Mari kita coba wujudkan dari /prompt/ yang kurang jelas menjadi lebih lengkap dan terstruktur dengan fitur-fitur yang ada di Cursor. Tapi sebelum itu, mari kita samakan persepsi terlebih dahulu dengan melihat cara kerja /coding agent/ dibelakang layar. Apa yang terjadi ketika kita mengetikkan instruksi lalu mengirimnya?

#+CAPTION: Cara kerja coding agent: dari prompt user → agent membaca konteks proyek → menjalankan aksi (edit file, jalankan terminal, dsb) → mengembalikan hasil, lalu berulang dalam /agentic loop/

** Memberi Instruksi dengan RULES / AGENTS.MD
Untuk hasil yang konsisten dan sesuai ekspektasi pada tugas yang kompleks, sebaiknya tambahkan instruksi yang jelas: mau buat apa, buatnya pakai apa, fiturnya apa saja dan bagaimana langkah-langkahnya. Untuk tugas sederhana (satu baris, satu file), instruksi minimal mungkin sudah cukup.

LLM tidak memiliki memori lintas sesi — setiap sesi baru dimulai dari konteks kosong. Di dalam satu sesi, instruksi perlu diulang jika konteks sudah melebihi jendela konteks (context window) atau jika instruksi awal sudah "tergeser" oleh percakapan panjang.

Cursor menyediakan [[https://cursor.com/docs/rules][Rules]] atau bisa juga menggunakan [[https://agents.md][AGENTS.md]] yang lebih umum digunakan. Rules disimpan di folder =.cursor/rules= dengan format =.mdc= (Markdown for Cursor — format markdown khusus Cursor yang bisa punya metadata seperti =glob= pattern untuk menentukan file mana saja yang aturannya berlaku, dan =alwaysApply= untuk menentukan kapan aturan dipakai).

Catatan: Versi lama Cursor menggunakan file =.cursorrules= di root proyek. Format ini sudah digantikan oleh folder =.cursor/rules/=. Kalau kamu punya =.cursorrules= yang sudah ada, Cursor masih membacanya untuk backward compatibility, tapi direkomendasikan untuk migrasi ke format baru.

Beberapa hal yang sebaiknya ada di rules:
- penjelasan singkat tentang proyek
- bagaimana cara kerja dan cara menjalankan proyek
- /coding standard/ atau arsitektur

Contoh struktur file dan folder untuk rules:

#+BEGIN_SRC
.cursor/rules/
  react-patterns.mdc       # Recognized as a project rule
  api-guidelines.md        # ⚠️ DIABAIKAN — ekstensi harus .mdc, bukan .md
  frontend/                # Organize rules in folders
    components.mdc
#+END_SRC

Perhatikan ukuran rules: setiap rule ditambahkan ke konteks setiap kali agent dipanggil. Rule yang terlalu besar (>50 baris) bisa mengurangi "daya pikir" agent karena token habis dipakai untuk konteks. Gunakan =glob= pattern untuk membatasi rule hanya ke file yang relevan, dan pertahankan rule tetap fokus.

Contoh isi file =.cursor/rules/frontend/components.mdc=:
#+BEGIN_SRC markdown
---
description: Component patterns for this project
glob: src/components/**/*.{tsx,astro}
alwaysApply: false
---
Gunakan functional components dengan TypeScript. Hindari class components.
Semua komponen harus punya unit test.
#+END_SRC

*** Rules dasar
Mari kita coba praktekkan penggunaan rules. Untuk membuat rules, ada dua cara:

1. *Lewat terminal*: Buka terminal, =cd= ke folder proyek kamu, lalu jalankan:
   #+BEGIN_SRC bash
   mkdir -p .cursor/rules
   #+END_SRC
   Kemudian buat file baru dengan ekstensi =.mdc= di dalam folder tersebut, misalnya =project-rules.mdc=.
2. *Lewat UI Cursor*: Buka Cursor → klik ikon Settings (⚙️) di sidebar kiri → pilih tab *Rules* → klik tombol =+ New Rule=. Sebuah form akan muncul seperti gambar di bawah.

#+CAPTION: Tampilan form untuk membuat rule baru di Cursor. Isi nama rule dan deskripsikan aturannya sesuai kebutuhan proyek.
#+NAME:   fig:Setting
[[./setting.png][Screenshot form Create New Rule di Cursor: input nama rule dan deskripsi aturan]]]

Isi nama dan deskripsikan aturannya.

#+BEGIN_SRC markdown
# Project: Show date and time realtime

## Tech Stack (non-negotiable)
- Frontend: Astro + TypeScript
- Styling: vanilla css
- No backend

## Product Constraints
- Theme: lime green
- Accessibility: big text, big buttons, readable type, clear color combination
#+END_SRC

Menariknya di cursor kita bisa memberi kondisi kapan saja rules ini berlaku. Ada empat mode yang bisa dipilih:
- *Always Apply*: Aturan dipakai di /setiap/ prompt, nggak peduli konteksnya apa.
- *Apply Intelligently*: Cursor yang memutuskan sendiri kapan aturan ini relevan berdasarkan isi prompt.
- *Apply to Specific Files*: Aturan cuma berlaku untuk file yang cocok dengan =glob= pattern (misal =*.tsx= untuk file React, atau =*.test.ts= untuk file testing).
- *Apply Manually*: Kamu yang panggil sendiri lewat =@Rules= saat lagi butuh.

Sekarang, dengan aturan yang baru ditetapkan, mari kita coba dengan /prompt/ generik.

#+BEGIN_SRC
refactor
#+END_SRC

Perintah /refactor/ diatas bisa dibilang tidak jelas dan bisa banyak interpretasi. Apa yang perlu di refactor? Apakah teknologinya, kodenya, testing, dsb.

Namun karena kita sudah memasang aturan, rules tersebut akan disertakan sebagai bagian dari system prompt setiap kali kamu mengirim perintah ke LLM. Dengan adanya instruksi "refactor code to match project conventions" di rules, LLM akan memprioritaskan perubahan yang menyelaraskan kode dengan aturan yang sudah ditetapkan.

** Menambahkan Skill
[[https://cursor.com/docs/skills][Skill]] adalah format berbasis markdown yang terdokumentasi secara publik — sehingga bisa dibagikan antar pengguna dan, dalam beberapa kasus, digunakan di tools lain yang mendukung format serupa. Meskipun belum menjadi standar resmi (seperti ISO atau W3C), format ini cukup terbuka untuk diadopsi dan bisa kamu download dari repo GitHub orang lain. Perlu diingat: beberapa skill mungkin membutuhkan dependensi tertentu atau ditulis untuk framework spesifik — periksa isi skill sebelum menggunakannya.
Skill ini sifatnya lebih portable — formatnya distandarisasi sehingga bisa dipakai di berbagai proyek tanpa perlu menyalin ulang. Berbeda dengan rules yang lebih terikat ke proyek dan kondisi penggunaannya bisa diatur (Always Apply, Apply Intelligently, Apply to Specific Files, atau Apply Manually). Skill hanya digunakan saat relevan: Cursor akan mengevaluasi apakah skill tersebut cocok dengan prompt yang kamu kirim. Jika skor relevansinya rendah, skill tidak akan disertakan ke dalam konteks.

*** Contoh Skill: Tidy TDD

Skill ini menerapkan *TDD (Test-Driven Development)* — cara menulis kode dengan membuat /test dulu/, baru menulis kode agar test-nya lulus. Siklusnya: *Red* (test gagal) → *Green* (test lulus) → *Refactor* (perbaiki struktur kode tanpa mengubah perilaku). Ditambah pendekatan *Tidy First* dari Kent Beck (salah satu penemu TDD) yang memisahkan perubahan struktur kode (=rename=, =extract method=) dari perubahan logika — jangan pernah campur keduanya dalam satu commit.

#+BEGIN_SRC markdown
For each next task, please do implement the test, then implement only enough code to make that test pass.

# CORE DEVELOPMENT PRINCIPLES
- Always follow the TDD cycle: Red → Green → Refactor
- Write the simplest failing test first
- Implement the minimum code needed to make tests pass
- Refactor only after tests are passing
- Follow Beck's "Tidy First" approach by separating structural changes from behavioral changes
- Maintain high code quality throughout development

# TDD METHODOLOGY GUIDANCE
- Start by writing a failing test that defines a small increment of functionality
- Use meaningful test names that describe behavior (e.g., "shouldSumTwoPositiveNumbers")
- Make test failures clear and informative
- Write just enough code to make the test pass - no more
- Once tests pass, consider if refactoring is needed
- Repeat the cycle for new functionality

[Sisa isi skill dipotong — lihat repo asli untuk versi lengkap]
#+END_SRC

** Delegasi Tugas dengan Subagent
Agent yang kita gunakan sejauh ini sifatnya generalis. Terkadang ada tugas yang membutuhkan spesialis. Cursor agent bisa mendelegasikan tugas tersebut ke subagent — kamu bisa memanggil subagent secara eksplisit dari prompt (misalnya: "minta subagent Explore untuk mencari semua file yang mengimpor modul X"), atau Cursor akan otomatis memanggil subagent yang tepat untuk tugas spesifik seperti menjalankan perintah Bash. Subagent juga dapat berjalan secara mandiri, punya context window sendiri, dan bisa dijalankan secara berbarengan sehingga tidak mengganggu agen utama.

Beberapa subagent yang sudah disediakan oleh Cursor:
- Explore: untuk pencarian dan analisa codebase
- Bash: Menjalankan perintah shell yang dibutuhkan
- Browser: Membuka dan menjalankan otomasi untuk aplikasi web

** Kustomisasi lebih lanjut dengan Hooks
Cara berikutnya untuk customize dan extend Cursor: Hooks memungkinkan kita menambahkan otomatisasi dan guardrail ke dalam workflow — misalnya memblokir perintah berbahaya sebelum dieksekusi, atau menjalankan formatter secara otomatis setelah agent selesai mengedit file. Intinya, hooks adalah skrip yang dieksekusi di trigger point yang diinginkan. Misalnya sebelum mengirim perintah ke LLM, sebelum menjalankan perintah shell, sebelum =npm install=, dsb.

Sebelumnya kita sudah lihat contoh hooks sederhana dengan file langsung di folder =.cursor/hooks/= (pendekatan simpel — cocok buat eksperimen cepat). Nah, Cursor juga punya cara yang lebih deklaratif lewat file =hooks.json= — kita bisa mendefinisikan trigger point dan script mana yang dijalankan secara lebih terstruktur (cocok buat workflow yang kompleks). Dua pendekatan ini bisa dipakai sesuai kebutuhan.

Berikut beberapa contoh penggunaan hooks:
- Run formatters after edits
- Add analytics for events
- Check for security or secrets
- Gate risky operations (e.g., SQL writes)
- Write collaboration logs

Contoh =beforeSubmitPrompt= — secara otomatis menambahkan konteks proyek ke setiap prompt:

#+BEGIN_SRC bash
#!/bin/bash
read -r input
prompt=$(echo "$input" | jq -r '.prompt')
cat <<EOF
{
  "continue": true,
  "prompt": "Project: web-app with Astro + TypeScript\\n\\n---\\n\\n$prompt"
}
EOF
#+END_SRC

*** Menulis Hooks
Kita bisa menambahkan hooks untuk secara aktif mengecek dan memblokir perintah yang berpotensi merusak. Misalnya melakukan =npm install= sebuah pustaka yang menambahkan banyak dependensi baru dan melanggar aturan "Keep 3rd party libraries to bare minimum" yang sudah ditetapkan di rules.

**** =./cursor/hooks.json=

#+BEGIN_SRC json
{
  "version": 1,
  "hooks": {
    "beforeShellExecution": [
      {
        "command": ".cursor/hooks/guard-npm.sh"
      }
    ]
  }
}
#+END_SRC

**** =./cursor/hooks/guard-npm.sh=

#+BEGIN_SRC bash
#!/bin/bash
set -euo pipefail

# Fail-safe: jika jq tidak tersedia, tolak perintah
if ! command -v jq &>/dev/null; then
  cat <<EOF
{
  "continue": false,
  "permission": "deny",
  "userMessage": "⚠️ Hook misconfigured: jq not installed. Command blocked.",
  "agentMessage": "Cannot verify command because jq is missing."
}
EOF
  exit 0
fi

read -r input
command=$(echo "$input" | jq -r '.command')

if echo "$command" | grep -qE "npm (install|i|add)\b"; then
  cat <<EOF
{
  "continue": false,
  "permission": "deny",
  "userMessage": "⚠️ New dependencies not allowed per Project Rules. Use existing ones only.",
  "agentMessage": "Respect 'Keep 3rd party libraries to bare minimum' constraint."
}
EOF
  exit 0
fi

# Allow everything else
cat <<EOF
{
  "continue": true,
  "permission": "allow"
}
EOF
#+END_SRC

Peringatan: Pattern matching sederhana seperti ini bisa dilewati — agent bisa mengedit =package.json= lalu menjalankan =npm install= (tanpa argumen) untuk menginstal dependensi baru. Untuk proteksi yang lebih ketat, kombinasikan hook ini dengan pemantauan perubahan file.

⚠️ =moment.js= sudah dalam mode maintenance-only dan tidak direkomendasikan untuk proyek baru.
Alternatif modern: =date-fns= atau =Intl.DateTimeFormat= bawaan JavaScript.
(Contoh dibawah sengaja menggunakan moment.js untuk mengilustrasikan hooks blocking — agent mungkin otomatis menyarankan alternatif modern.)

** Customization Marketplace
Cursor juga menyediakan marketplace untuk kustomisasi — isinya macem-macem: ada yang berupa rules, ada yang berupa skills, subagents, atau hooks — bahkan ada yang mengombinasikan beberapa jenis sekaligus. Kita bisa menggunakan hasil kustomisasi buatan teman-teman komunitas. Cara mengaksesnya: buka Cursor → klik ikon puzzle (🧩) di sidebar kiri → pilih tab *Marketplace*. Atau langsung kunjungi [[https://cursor.com/marketplace][cursor.com/marketplace]].

Beberapa contoh yang bisa kamu eksplorasi:
- *Continual Learning*: skill yang mengajarkan agent untuk mencatat keputusan dan learnings dari sesi ke sesi — jadi agent kamu makin lama makin paham proyek.
- *Superpower*: koleksi shortcut dan optimasi workflow untuk produktivitas maksimal.
- *Compound Engineering*: pendekatan untuk mendokumentasikan solusi dari masalah yang sudah terpecahkan — supaya kita nggak ulangi kesalahan yang sama.

** Penutup
Cursor bukan sekadar editor kode dengan LLM di dalamnya. Cursor adalah platform yang sangat bisa dipersonalisasi untuk mengubah cara kita bekerja sebagai developer. Dengan memanfaatkan fitur-fitur seperti:

Rules (=.cursor/rules=) → Memberikan konsistensi dan alignment proyek
Skills → Mengajarkan LLM cara kerja yang lebih baik dan portable
Subagent → Memberikan spesialisasi tugas
Hooks → Memberikan kontrol dan guardrail otomatis
Customization Marketplace → Memanfaatkan pengetahuan komunitas

Dengan rules, skills, dan hooks yang tepat, kita bisa mengurangi variabilitas output dan meningkatkan konsistensi dengan standar proyek — mendekati, meskipun tidak sepenuhnya setara dengan, produktivitas rekan kerja manusia yang sudah familier dengan codebase. Hasilnya tidak akan 100% sempurna, tapi error-nya cenderung lebih terprediksi dan lebih mudah diperbaiki.
Intinya: semakin baik kita mendefinisikan apa yang kita mau, semakin baik pula hasil yang diberikan Cursor. Prompt yang bagus tetap penting, tapi fondasi yang kuat (rules + skills + workflow) memastikan konsistensi tanpa perlu menulis ulang instruksi setiap kali.

*** Quick Start (5 Menit Pertama)

Baru pertama kali dan mau langsung nyoba? Ikuti 3 langkah ini:

1. Buka proyek kamu di Cursor (atau buat folder baru)
2. Buat file =.cursor/rules/project-info.mdc= dan isi dengan:
   #+BEGIN_SRC markdown
   # Project: [nama proyek kamu]

   ## Tech Stack
   - [teknologi yang kamu pakai]

   ## Aturan Penting
   - [aturan spesifik proyek kamu]
   #+END_SRC
3. Kirim prompt pertama kamu ke agent Cursor (bisa lewat =Cmd+I= di macOS atau =Ctrl+I= di Windows/Linux)

Itu aja! Kamu sudah punya fondasi personalisasi. Lanjut baca materi diatas untuk level selanjutnya.

*** Glosarium

- *5W1H*: Metode menjawab What/Why/Who/Where/When/How untuk menjelaskan sesuatu secara lengkap.
- *Astro*: Framework web untuk bikin website statis dan interaktif.
- *Coding Agent*: AI yang bisa melihat file proyek, mengedit kode, menjalankan perintah terminal, dan membaca hasilnya — bukan cuma chat.
- *Cursor*: Code editor berbasis VS Code yang punya AI/LLM bawaan untuk bantu menulis kode.
- *Hooks*: Skrip yang dieksekusi otomatis di trigger point tertentu (sebelum prompt dikirim, sebelum shell command, dll).
- *=jq=*: Command-line tool untuk membaca dan mengolah JSON.
- *LLM (Large Language Model)*: Model AI yang bisa memahami dan menghasilkan teks. Contoh: GPT-4, Claude, Gemini.
- *=.mdc= (Markdown for Cursor)*: Format markdown khusus Cursor dengan dukungan metadata seperti =glob= dan =alwaysApply=.
- *Milestone*: Tonggak pencapaian dalam pengembangan.
- *Piramida Berpikir*: Kerangka untuk memecah masalah dari abstrak ke konkret.
- *PRD (Product Requirements Document)*: Dokumen yang menjelaskan fitur apa yang harus dibuat.
- *Rules*: Instruksi yang selalu disertakan dalam setiap prompt untuk memberikan konteks proyek ke LLM.
- *Skills*: Modul portable yang mengajari LLM cara mengerjakan tugas spesifik (contoh: TDD, frontend design).
- *Slices*: Potongan fitur kecil yang bisa dikerjakan dan di-review dalam satu waktu.
- *SPEC (Spesifikasi Teknis)*: Dokumen yang menjelaskan bagaimana cara membuat fitur.
- *Subagent*: Agen spesialis yang bisa didelegasikan tugas tertentu oleh agen utama.
- *TDD (Test-Driven Development)*: Metodologi menulis kode dengan membuat test dulu, baru implementasi. Siklus: Red → Green → Refactor.
- *Tidy First*: Pendekatan dari Kent Beck yang memisahkan perubahan struktur kode dari perubahan logika.
- *Trigger Point*: Momen spesifik saat Cursor mengeksekusi hook (misal =beforeSubmitPrompt=, =beforeShellCommand=).
- *User Stories*: Deskripsi fitur dari sudut pandang pengguna.
- *Vitest*: Tools untuk menjalankan test di JavaScript/TypeScript (mirip Jest).
